# Desktop Signal Monitor — QA / AutoQA Test Task

Небольшой учебный стенд для тестирования Desktop-приложения мониторинга сигналов.

Проект собран вокруг одного основного пользовательского сценария:

**TCP-сервис → Desktop-приложение → отображение сигналов → UI-автотест.**

Здесь я хотел показать не только сам автотест, но и полный стенд, на котором его можно реально запустить и проверить.

---

## Что проверяем

Desktop-приложение получает от TCP-сервиса 10 сигналов и отображает их в таблице.

Для каждого сигнала отображаются:

- ID;
- имя;
- значение;
- качество;
- время получения.

Основной автоматизированный сценарий:

1. Запустить TCP-сервис-симулятор.
2. Запустить Desktop-приложение.
3. Нажать **«Подключиться»**.
4. Дождаться получения данных.
5. Проверить, что получены все 10 сигналов.
6. Проверить основные поля сигналов.

# 1. Чек-лист

1. Проверить запуск Desktop-приложения без ошибок и корректное отображение главного окна.
2. Проверить начальное состояние приложения: отсутствие подключения и отсутствие данных в таблице.
3. Проверить подключение приложения к TCP-сервису на порту `2001`.
4. Проверить изменение состояния интерфейса после успешного подключения.
5. Проверить получение всех 10 сигналов.
6. Проверить корректность отображения ID, имени, значения, качества и времени.
7. Проверить обновление изменяющихся значений без зависания интерфейса.
8. Проверить корректность поля «Качество».
9. Проверить актуальность времени получения сигнала.
10. Проверить работу кнопки «Обновить».
11. Проверить поведение приложения при недоступном TCP-сервисе.
12. Проверить восстановление соединения после перезапуска TCP-сервиса.
13. Проверить отсутствие дублей сигналов после нескольких обновлений.
14. Проверить корректное завершение приложения при активном TCP-соединении.
15. Проверить стабильность приложения при длительном получении изменяющихся сигналов.

# 2. Критичный сценарий

## Подключение к сервису и получение всех 10 сигналов

Основное назначение приложения — получать данные от удалённого сервиса и отображать их оператору.

Поэтому критичным считаю сценарий, который проверяет весь путь от подключения до отображения данных.

### Шаги

1. Запустить TCP-сервис-симулятор.
2. Запустить `Signal Monitor`.
3. Нажать **«Подключиться»**.
4. Проверить статус подключения.
5. Дождаться получения сигналов.
6. Проверить наличие 10 сигналов в таблице.
7. Проверить ID `1–10`.
8. Проверить заполненность основных полей.

### Ожидаемый результат

Приложение устанавливает TCP-соединение, получает все 10 сигналов и корректно отображает их в таблице без дублей и ошибок.

# 3. Автоматизация

Для автоматизации используется:

- **Python** — язык разработки;
- **pytest** — тестовый фреймворк;
- **pywinauto** — автоматизация Desktop GUI через Windows UI Automation;
- **PySide6** — Desktop-приложение;
- **socket** — TCP-взаимодействие с симулятором.

Основной автотест:

```text
tests/test_signals.py
```

Тест автоматически:

1. запускает необходимые процессы;
2. находит окно `Signal Monitor`;
3. находит кнопку **«Подключиться»**;
4. нажимает кнопку;
5. ждёт получения данных;
6. находит таблицу;
7. проверяет наличие 10 сигналов;
8. проверяет ID;
9. проверяет обязательные поля;
10. проверяет качество и время.

# 7. Запуск

## Запуск TCP-сервиса

В первом терминале:

```powershell
python simulator\server.py
```

После запуска:

```text
Signal simulator listening on 0.0.0.0:2001
```

Сервис продолжает работать и ждать подключения.

## Запуск Desktop-приложения

Во втором терминале:

```powershell
python application\main.py
```

Откроется окно `Signal Monitor`.

Нажать:

**Подключиться**

После успешного соединения в таблице должны появиться 10 сигналов.

---

# 8. Запуск через Docker

TCP-симулятор также можно запустить через Docker Compose:

```powershell
docker compose up --build
```

После запуска контейнера Desktop-приложение запускается локально:

```powershell
python application\main.py
```

Docker используется только для симулятора. Desktop GUI запускается непосредственно в Windows, так как автотест работает через Windows UI Automation.

Перед запуском автотеста не нужно вручную запускать второй экземпляр `Signal Monitor`.

# 10. Что проверяется в автотесте

Главная проверка — количество полученных сигналов:

```python
assert len(rows) == 10
```

Дополнительно проверяются:

- ID сигналов;
- имя;
- значение;
- качество;
- время получения.

То есть тест проверяет не просто открытие TCP-порта, а пользовательский сценарий:

```text
Запуск приложения
       ↓
Поиск окна
       ↓
Кнопка «Подключиться»
       ↓
TCP-соединение
       ↓
Получение данных
       ↓
Отображение в таблице
       ↓
Проверки
       ↓
PASSED
```

# 11. Почему используется pywinauto

`pywinauto` позволяет работать с Desktop-приложением примерно так, как это делает пользователь:

- найти окно;
- найти кнопку;
- нажать кнопку;
- найти таблицу;
- получить данные из UI;
- выполнить проверки.

При разработке автотеста пришлось проверить, как элементы Qt-приложения реально представлены в Windows UI Automation, и скорректировать локаторы.

Это важно для Desktop UI-тестов: элемент, который визуально есть на экране, не всегда доступен в UI Automation именно с тем `control_type` или идентификатором, который ожидаешь увидеть.
